# ADR-0003：35 个平铺模块作为历史快照

- **状态**：已接受
- **日期**：2026-10-27
- **决策者**：LandFairy
- **更正（2026-10-28）**：标题原写「36 个」，实际是 **35 个**——第 00 章是方法论、没有代码模块，
  模块从 `step-01-map-container` 到 `step-35-graduation`。决策本身不变。

## 背景

本书是**渐进式**的：第 12 章的能力是第 11 章的超集。这种递进关系有三种组织方式：

1. **每章一个模块**（`tiny-spring-step-01` … `-35`），每份都是完整可运行副本
2. **单模块 + 每章一个 git branch / tag**
3. **单模块只保留最新代码** + 文档里贴每章的 diff

## 决策

采用**方案 1：每个章节目录是一个完整的、可独立运行的 Maven 模块**。

```text
tiny-spring-tdd/
├── step-01-bean-container/
├── step-02-bean-definition/
├── ...
└── step-35-reading-real-spring/
```

每个模块自带 `main` / `test`，能单独 `mvn -pl step-XX-xxx test` 运行。

## 后果

### 正面

- **打开就能跑**。新手不需要懂 git branch、不需要会切 tag、不需要自己 apply diff。
  在 IDEA 里展开目录树，点任意一章的测试就能运行——这是最低的认知门槛。
- **对照天然成立**。读者想比较第 8 章和第 9 章的差别，两个目录直接 diff 即可，
  不用切分支（切分支会丢失 IDE 的上下文）。
- **每章都是一个"可编译的最小完整物"**。这强迫我们每章结束时框架必须处于自洽状态，
  不能留下"下一章才补上"的半截代码。

### 负面（必须认账）

**维护成本是 N 倍。** 第 5 章修一个 bug，第 6~35 章都要同步（30 处）。
这不是技术问题，是**承诺问题**——所以必须先把政策定死，否则每次遇到都会被当成新争论。

**政策：只向前修。**

- 历史章节的代码**冻结**。除了下面两类，一律不回改。
- **例外一：正确性 bug**。如果某章代码编译不过、测试不绿、或断言是错的，
  **必须**在同一次提交内改完该章及其后所有章节。
- **例外二：安全/环境性失效**（例如某个 API 在新 JDK 被移除）。
  同样全链同步。
- 同步工具：`scripts/propagate.sh`，把某章的补丁顺序向后 apply，冲突即停并要求人工介入。

**代码重复让读者困惑"哪个是最新版"。**
缓解：根 README 用一张明确的索引表说明"读第几章就看哪个目录"，
并在每章目录内放 `README.md` 指向本章正文。

## 备选方案

**方案 2（branch / tag）**
无重复，diff 天然干净。但要求读者会用 git 切分支，而目标读者"只是会 Java"。
且切分支后 IDE 索引重建、调试上下文丢失，对学习是纯负担。**已否决。**

**方案 3（单模块 + 文档贴 diff）**
主线最干净。但读者想"看第 7 章的完整代码"时必须靠 diff 手工复原，
一旦某一章 diff 有误就无法验证。**已否决。**

## 相关决策

- `scripts/propagate.sh` 本身是一张独立的 infra ticket，在第一个里程碑之后落地。
- 每章提交两次（代码 / 文档），每章打 tag；每 7 章左右构成一个 milestone 并出 PR。
