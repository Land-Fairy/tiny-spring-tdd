## 三、P1

1. `AbstractApplicationEventMulticaster.java:70` 的 `removeApplicationListener` 走 `resolveListener()` → `getBean`（`:107`），**删一个监听器会把所有监听器 Bean 全部实例化**，关闭期还可能抛异常；上游同方法只在两张登记表里删，不做解析。该方法是全书零调用的。
2. `AbstractApplicationContext.java:352-355` 的 `cancelRefresh()` 不重置 `earlyApplicationEvents`（`:177` 初始化、`:305` 才置 null）→ 启动失败后每次 `publishEvent`（`:112-113`）都往永不清空的 Set 里塞事件，静默丢失且无界增长。
3. `AbstractApplicationContext.java:403-410`：注释称「必须吞并只记日志」并引上游 `warn`，实际 `catch (RuntimeException ignored)` 完全没记；与 `DisposableBeanAdapter:24`「本书没有日志设施」的披露口径不一致——**要么两处都声明「吞掉」，要么两处都收进列表**。
4. 测试三处（E2，工程效率工程师）：`ApplicationEventMulticasterTests.java:82-98` 的「名字登记不会立刻 getBean」在本设置里不可测（`:85` 已 `registerSingleton`）；`ListenerRegistrationTests.java:24` 的 `isNotNull()` 恒真；`ListenerRegistrationTests.java:44-47` 的 `postProcessBeanFactory` 只调 `super`。
5. `docs/chapters/15-events.md:647` 引「不要在这里初始化 FactoryBean」的上游注释标 `:919-920`，实际 `:917-918`（P2）。
6. 「多播器 / 广播器」「发布 / 分发 / 投递」各成一套，建议统一到词表。

## 四、读者会在哪一段放弃

不会放弃——这是七章里**唯一没有 A/B 类缺陷**的一章。表格、行号、示例全部经得起核。真正的问题在开头那段类注释：读者读到「其余九步是空的」会困惑，因为他刚在前面几章看着这些步骤被填满。

## 五、总判词

本章是**设计最优雅**的一章：事件是不可变的「事实」，容器只负责把事实送到按类型登记的监听器手上，`SimpleApplicationEventMulticaster` 不到 100 行就吃下上游 400 多行。它的失分全在**跨章复制残留**（C1/C2）和**一处过度自信的异常判别**（D1）：把「上游的启发式」写成了「本书的保证」。
