## 三、P1

1. `docs/chapters/09-application-context.md:454` 标上游 `refresh()` 为 `:588-660`，实测为 **:588-658**（660 行已是下一个 javadoc 的起始）。
2. `step-09-…/context/support/ClassPathXmlApplicationContext.java:47-53` 的 `getLocation()` javadoc 说「测试用来确认它到底读了哪一份配置」，全书（核到 step-35）零调用——一个为说明而存在、却无人使用的访问器。
3. `AbstractApplicationContext.java:377` 的 `getParentBeanFactory()` 不过 `assertBeanFactoryActive()`，与 `:291`「所有取 Bean 的方法都先过这一关」互斥；正文说它是唯一例外，代码注释没写这一行。
4. 「监听话册」（`docs/chapters/09-application-context.md:60`）是错字，应为「监听器」——一旦写错就没法 `grep` 到。

## 四、读者会在哪一段放弃

「失败还能再试」那一段（正文 §3.4）。书上把它当作 `refresh()` 设计的优点来讲，读者如果照着写一个「失败后重试」的小实验，会直接撞上 `does not support multiple refresh attempts`。这是全书第一次「书上的承诺，代码当面否认」。

## 五、总判词

本章是全书的**骨架章**：把散在前八章的零件装进一个 12 步的 `refresh()`，每一步都能被覆写、顺序不可改——这个设计值得学。它的失分不在结构，在**状态机口径**：`active` / `closed` / `refreshed` 三个标志没有一个地方被完整地说清楚，注释、正文、测试各说一套。C1/C2/E1-E3 五条都指向同一件事：**这一章缺一张状态图**。
