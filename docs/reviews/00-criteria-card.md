# 判据卡 v1 — tiny-spring-tdd 全量评审的判定标准

> 所有评审角色（Lead / 6 位平台专家 / Spring 源码教学评审官）共用这一份判据。
> 出现分歧时，以本文件的「§7 裁决顺序」为准；本文件没写的，不许当扣分理由。
> 生成依据：`code-quality-heuristics-brief.md`（Effective Java 官方目录 / Clean Code 与 Ousterhout 书面交锋 / Spring 官方 Code-Style / Checkstyle 配置）、仓库实测（35 个 step 模块、305 文件、18109 行主代码、446 个 @Test）、用户裁决（四条行为准则 + 教学直白优先）。

---

## §1 证据分级（每条结论必须落在其中一层）

| 层 | 含义 | 要求 |
|---|---|---|
| **E1** | 仓库或 Spring 源码中的事实 | 必须给 `文件:行号`，且行号必须真实可打开 |
| **E2** | 真实专家说过的原话 | 必须给可查出处（书页号 / issue / 论文 / 官方文档 URL） |
| **E3** | 评审者的判断 | 必须用"我认为"开头，允许被否决，不得伪装成事实 |

**零虚构红线**：任何伪造的行号、类名、模块路径、issue 编号、commit hash，该份评审整体作废。本仓已发生过两次此类事故（把 `step-01-map-container` 写成不存在的 `step-01-xml-beanfactory`；issue #55 声称 ArchUnit 为零而实际存在 `LayeringTests` + `archunit-junit5 1.3.0`）。

## §2 严重度定义

- **P0 — 新手照抄会出错**，满足任一：
  1. 语义错误：照抄后在真实场景产生错误行为（线程安全、顺序、生命周期、代理时机）；
  2. **文档与代码矛盾**（文档漂移一律 P0，因为读者会相信文档）；
  3. **虚假能力声明**：注释/文档/README 声称支持某能力，实际不支持或只支持一部分；
  4. 声称"简化"但保留了一个会导致后面章节推翻的结构。
- **P1 — 明显欠债，照抄不出事故**：命名失真、重复代码、错误处理吞异常、测试只覆盖 happy path。
- **P2 — 可选改进**：每章最多 5 条。超过 5 条说明评审者在凑数。

**不作为扣分理由**（写进这一节是为了压噪音）：
`@author` 标签的有无、Tab/空格、行宽、文件长度、注释密度、是否使用 lambdas/stream/var（框架内部实现允许，教学段落必须有等价展开）、个人命名口味、`Optional` 用法偏好、是否 JDK 21 特性。

## §3 六道闸门：哪些能机器判、哪些只能人判

| 闸门 | 工具 | 能机器判什么 | 机器**判不了**什么（评审必须补） |
|---|---|---|---|
| 格式 | `spring-javaformat:validate` | 缩进/换行/import 通配 | 格式对了但命名在撒谎 |
| 依赖红线 | Enforcer JDK[17,22) + 禁 `org.springframework*` | 依赖越界 | 用 JDK 类实现了 Spring 已有更好方案 |
| 静态 | Checkstyle(error) + PMD(10 条) | 方法≤40 行、参数≤5、耦合≤15、10 条 PMD | 通过闸门但结构纠缠、认知负担高 |
| 覆盖率 | JaCoCo LINE 0.80 / BRANCH 0.70 | 行/分支覆盖 | **断言是否有效**——空断言也能满覆盖 |
| 分层 | ArchUnit 4 条规则（`LayeringTests`） | 包依赖方向 | 规则之外的错误依赖 |
| 传播 | `scripts/check-propagation.sh` | 35 个 step 副本是否同步 | 该改没改（漏改） |

> 结论：**六道闸门全绿 ≠ 可以照抄**。评审的价值必须落在"机器判不了"那一列。

## §4 六个评审视角（各视角的判据 + 什么不算它的问题）

### V1 新手可读性 —— 唯一最高优先级
用户画像：只用过 `@Autowired`、没读过框架源码、会照抄。
四问，答不上即 FAIL：
1. 只看 `main` 或测试，3 分钟内能否指出"从哪进、到哪算完"？
2. 异常路径：抛异常时已创建的对象/已注册的单例/已开的流谁收拾？
3. 四个概念（`BeanDefinition` / `BeanFactory` / `ObjectFactory` / `BeanDefinitionRegistry`）在**结构上**分开，还是靠注释讲分开？
4. 删掉全部注释，读者还能说出这个类做了什么吗？
- **不算它的问题**：注释太多、代码不够"简洁"、没用设计模式。

### V2 结构与深模块
判据（Ousterhout）：接口小而实现厚 = 深；为拆而拆导致接口变多、调用要跳 5 个文件 = 浅 + 纠缠。
三个复杂度症状作为扣分依据：**变更放大 / 认知负担 / 未知的未知**。
- 检查点：新增一个 Bean 概念时，要改几个文件？改 5 个以上 = 变更放大。
- **不算它的问题**：没有用接口 + 实现类分离、没有分层包结构（教学项目扁平是 ADR 已定的）。

### V3 与真实 Spring 的一致度
只在涉及以下主题时启用，且必须核到真实源码行号：三级缓存查询顺序、`refresh()` 十二步、`doCreateBean` 四段、`PriorityOrdered` 三档排序、组件扫描用 ASM 不 `Class.forName`、`@Configuration` 的 CGLIB 拦截、`ReflectiveMethodInvocation#proceed`、`ResolvableType`。
**刻意偏离不扣分**，条件是：类注释里有一行说明砍掉了什么 + `@see` 真实类全限定名（ADR 已定）。**没声明的偏离 = P0（虚假能力声明）**。

### V4 简洁与优雅
- 《Effective Java》3e 条目号已核对官方目录，引用以下编号（历史错误已修正）：4 工具类不可实例化、15 最小化可见性、16 组合优于继承、17 最小化可变性、24 优先静态成员类、26 不用原生类型、34 枚举代替 int 常量、40 一致 `@Override`、49 检查参数、50 防御性拷贝、53 慎用可变参数、55 返回空集合、56 为暴露 API 写文档、57 最小化局部变量作用域、58 for-each 优于传统 for、62 不用字符串代替更合适类型、64 用接口引用、65 优先接口而非反射、69 只在异常情况用异常、70 可恢复用受检异常、71 避免不必要受检异常、72 优先标准异常、73 异常与抽象对应、74 文档化抛出异常、75 消息含失败信息、76 失败原子性、77 不忽略异常、78 同步访问共享可变数据、79 避免过度同步、80 Executor 优于线程、81 并发工具优于 wait/notify、82 线程安全写进文档、83 慎用延迟初始化、84 不依赖线程调度器、85 其他手段替代方法名序列化、88 防御性拷贝参数。
- **Clean Code 与 Ousterhout 的裁决**：Martin 主张"函数几乎不该超过 20 行""注释总是失败"（*Clean Code* p.34–35、p.54）；Ousterhout 原话"I was horrified…有大量重要信息根本无法用代码表达，这不是表达能力的失败"（`github.com/johnousterhout/aposd-vs-clean-code`，2024–25 书面交锋）。**本项目采 Ousterhout**：注释承载"为什么"，不承载"做了什么"；不为拆小而拆小。
- 教学语言红线：三行直白 > 一行 lambda + 嵌套 stream。
- **不算它的问题**：注释多、方法不够短、没用 builder/策略/工厂。

### V5 测试有效性（唯一能证伪覆盖率的水位）
逐条检查：
1. **空断言识别**：`assertDoesNotThrow` / `assertNotNull` / 只 `verify` mock 无返回值断言 → 命中即 P1；若该测试是本章核心行为的唯一测试 → P0。
2. **反向验证**：把被测方法改成 `return null` / 抛异常，测试会不会红？（对 3 个核心类用 PIT 变异测试实测）
3. **测的是行为还是实现**：断言里出现私有字段反射、`assertEquals(3, list.size())` 而不断言内容 → P1。
4. **命名**：`testGetBean1` → P2；`shouldThrowWhenBeanMissing` → 合格。
- **不算它的问题**：测试代码重复、没有用 parameterized test、覆盖率略高于底线。

### V6 文档与工程一致（本仓已有 6 处实证漂移，全部按 P0）
必须核对的既有矛盾清单（评审时逐条确认状态）：
1. 文档写"类耦合度 ≤10"，`config/checkstyle/checkstyle.xml:97` 实为 `max=15`；
2. ADR-0003 承诺"每章 README"，实际 0 个；
3. `LayeringTests` 的 Javadoc 写"两条"规则，实际 4 条；
4. `BeanDefinition` 的 Javadoc 声称 10 个方法，实际 27 个；
5. issue #55 声称 ArchUnit 为零，实际存在；
6. issue #52/#53/#55 引用不存在的模块 `step-01-xml-beanfactory`（真实为 `step-01-map-container`）。
新增漂移同样按 P0 处理；发现即列入报告，**但不在本次评审中顺手修改**（外科手术式改动原则）。

## §5 判决（v1.1：按 P0 **类别**定，不按修法范围定）

> v1.0 的「PASS-WITH-FIXES = 有 P0 但修法局部」与「FAIL = 存在文档漂移」互相重叠，导致 ch01 示范里 6 位专家分出 3 FAIL / 4 PASS-WITH-FIXES。现改为只看**缺陷属于哪一类**，与好不好修无关——"好修"不等于"不严重"，教学仓库尤其如此。

P0 分五类：

| 类 | 名称 | 判定特征 |
|---|---|---|
| **A** | 虚构引用 | 指向不存在的类/方法/行号/上游事实。读者按图索骥必然失败 |
| **B** | 量化矛盾 | 文档与代码在同一事实上给出互斥的数字或结构描述（行数、条数、字段数、命名位置） |
| **C** | 语义/契约缺陷 | 代码行为与自身注释/异常消息/命名承诺不一致；照抄产生错误行为 |
| **D** | 兑不了的教学承诺 | 承诺"后面章节会…"，实测到 step-35 未兑现 |
| **E** | 闸门失效 | 测试或脚本看似在守、实际守不住（断言恒真、规则空集放行、脚本单边检测） |

| 判决 | 条件 |
|---|---|
| **PASS** | 无 P0，且 V1 四问全过，且本章至少 1 条能失败的断言 |
| **PASS-WITH-FIXES** | 只有 C 类或 E 类 P0（代码行为/守门问题），无 A/B/D |
| **FAIL** | 存在任一 **A / B / D** 类 P0（读者会被引到错误的地方或相信假话） |

补充：同一缺陷在 35 个副本中各记一次（因为每章都是可独立阅读的教材），但在第 01 章记"原件"，后续章标 `同 ch01 A1`。

## §6 每章产出固定结构

`docs/reviews/chNN.md`：判决 → 一句话结论 → 🔴P0（每条含 `文件:行` + 最小修法 + 依据）→ 🟡P1 → 💭P2（≤5）→ 六维评分（可读性 / 结构正交性 / 与真 Spring 一致度 / 测试有效性 / 文档一致度 / 优雅度，各 1–5）→ 🧭 我会卡在哪（≥1 条，必须具体到行）→ 📚 依据清单（E1/E2/E3 分列）。

## §7 裁决顺序（冲突时按此优先级）

1. **新手可照抄**（V1）——压过一切。
2. **不让读者相信假话**（V3 的虚假声明 + V6 文档漂移）。
3. **测试是否真的在验证**（V5）。
4. **结构与深模块**（V2）。
5. **简洁与优雅**（V4）。
6. 机器闸门已判定的项（§3 左列）不再重复讨论。
